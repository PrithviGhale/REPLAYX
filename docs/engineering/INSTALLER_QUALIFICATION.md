## Automated qualification on GitHub-hosted Windows

The [manual workflow](../../.github/workflows/installer-qualification.yml) uses a fresh Windows Server 2025 x64 VM for each case. It installs the exact packaged NSIS executable. Scope `clean` runs just the clean install. Scope `upgrades` runs separate Alpha.4, Alpha.9, rc.1 and rc.2 installations. Scope `all` includes the five scenarios. Every case uninstalls the candidate after the checks.

1. Use the local QA archive at `test-output/rc3-final-preflight/legacy-cleanup-bundle/REPLAYX-installer-qa-rc3-legacy-cleanup.zip`. Its SHA-256 is `5C2374E961EE2F3C8B406A35D6889F23BB23220C06CC8FE8BCBC546D9F0D0952`. The archive contains the corrected rc.3 setup, four baseline installers and a generated MKV fixture. The script checks the outer digest and verifies each of the six members against committed size, SHA-256 and version pins before executing anything.
2. After approval, make the manual workflow available on the default branch and stage the archive as a release asset on an unpublished QA draft in the same repository. Keep this separate from the public release package. Use its numeric asset ID and SHA-256 as workflow inputs. Making the workflow available on the default branch also runs the repository's existing push checks. The read-only workflow token returned HTTP 403 for the draft. Obtain an expiring URL for the one asset from the authenticated GitHub release-asset API. Store only that short-lived URL in the repository Actions secret `REPLAYX_QA_SIGNED_ASSET_URL` and remove the secret after testing. The workflow also supports releases readable with its default read-only token. GitHub checks the asset access and the workflow checks the expected SHA-256.
3. Dispatch `candidate_version=0.4.0-rc.3`, `scope=clean` first. Review the run summary and per-scenario logs, then dispatch `scope=upgrades` after the smoke run succeeds. The workflow retains registry snapshots, process exit codes, startup signals, FFmpeg decode progress and failure details for seven days. Only the `logs` folder is retained as an Actions artifact.
4. For the stable run, use the same baseline installers and generated sample, replace `Candidate-setup.exe` in the archive with the exact final Windows-signed installer bytes, and include the final `latest.json`. Calculate a new outer SHA-256 and dispatch `candidate_version=0.4.0`. The harness checks Authenticode and timestamps on the installer, app and native worker. It also verifies that the final manifest selects the expected URL and that its signature covers those exact bytes with the current Tauri key.

The Windows Server workflow tests the silent per-user NSIS path, installed metadata and payload, selected settings and an existing clip checksum across upgrades and uninstall. It decodes the clip with the installed FFmpeg and checks for a live app window and WebView2 child where the runner has an interactive session. The settings and recording are fixtures created inside the runner. Interactive installer screens, Windows 11 Home behavior, WebView2 control interaction, physical recording and automatic updater download, installation and restart need separate evidence. Record unavailable checks as blocked. ## GitHub-hosted qualification result

The rebuilt rc.3 installer passed all five silent NSIS scenarios on November 19, 2026, in fresh Windows Server 2025 Datacenter runners with WebView2. The [clean run](https://github.com/PrithviGhale/REPLAYX/actions/runs/44556397658) and [four upgrade runs](https://github.com/PrithviGhale/REPLAYX/actions/runs/44556612474) used the same verified archive and QA commit `7fc275d`. Copies of the raw evidence are under `test-output/rc3-final-preflight/github-actions`.

The original Alpha.9 upgrade left four retired diagnostic executables in the installation directory after uninstall. The [NSIS cleanup hook](../../src-tauri/installer/legacy-program-cleanup.nsh) removes the known legacy program files after installing successfully over a registered REPLAYX installation. The 180-second fixture follows Alpha.4's supported replay lengths. Tests observed two legacy tools before the Alpha.4 upgrade and four before the Alpha.9 upgrade. Both had zero remaining after upgrade.

Every case created a REPLAYX window and a WebView2 child, decoded all 600 sample video frames and all three audio tracks with installed FFmpeg, and preserved the selected settings and exact recording checksum after uninstall. Uninstall removed the install directory, registration and shortcuts. The rc.1 and rc.2 fixtures also preserved the stored engine preference and Crosshair color. The harness sometimes stopped its own test process after window close, so graceful exit remains outside this qualification.

The rebuilt installer SHA-256 is `C57F3023D532FD5664FF022369097354A5A23C3318AC83AF862C30BB38BAAAF1`. Its app, worker and ten pinned FFmpeg runtime files match the original candidate byte for byte. The locally archived original bundle and cloud QA results document the issue before the fix.

## Optional interactive qualification in a disposable Windows 11 guest

The test kits map only their staged installers and map them read-only. The guest configuration disables networking, microphone, camera, clipboard and printer sharing. Opening a kit starts a clean Windows Sandbox with no startup command. Use a disposable Windows 11 VM snapshot if Sandbox is unavailable. Use a guest with WebView2 for the compact installer. Verify the selected runtime and keep Windows security protections enabled throughout.

## Run each scenario from a clean guest

1. **Clean install and uninstall.** Open the clean kit, compare the setup hash to the manifest, run Candidate-setup.exe and verify product, version, destination selection, progress, desktop shortcut option and launch. Check Settings and whether the bundled worker and FFmpeg runtime are present. Create a test clip inside the guest and a marker file in the selected clips folder. Uninstall through Installed Apps with the data-removal option unchecked. Verify the application and shortcuts are removed and both files remain.
2. **Alpha.4 and Alpha.9 upgrades.** Start a separate fresh guest for each baseline. Run Previous-setup.exe, launch and change a Crosshair-independent setting such as replay length. Save a clip if available, or make a marker in the chosen clips folder. Exit REPLAYX from the tray. Run Candidate-setup.exe and verify a single installed REPLAYX entry, prior settings and files, worker and runtime placement, and the upgrade launch. Uninstall and verify retained data.
3. **rc.1 and rc.2 upgrades.** Start a fresh guest for each baseline. Save a Crosshair configuration and select an engine before upgrading. Confirm the preset survives and the engine preference is retained. Close the guest when complete.
4. **Signed updater.** Before publication, verify the signed installer and its final manifest and keep an Alpha.9 guest snapshot. Once publication is approved, run **Check Now** in that isolated Alpha.9 installation. Install the offered stable update and verify restart, settings and the same clip checksum. Published rc versions follow the rc channel. Alpha.9 uses the manual installer to move to rc.3.

The guest qualifies setup and data preservation. A short real-device A/V spot check of the final candidate can confirm the AAC fix on physical equipment. Additional FPS benchmarking is unnecessary for this release gate.

## What to obtain for a signed build

- A publicly trusted Windows Authenticode code-signing certificate with the Code Signing EKU, an accessible signing key through its provider and its RFC 3161 timestamp URL. The build account needs access to the certificate in Current User → Personal. Keep any hardware token, PIN or cloud signing credentials private.
- A Windows SDK SignTool executable path on the signing runner. Provide the certificate thumbprint, timestamp URL and SignTool path to scripts/build-rc.ps1. The worker, app and installer must pass Authenticode policy and timestamp checks.
- For managed Microsoft Artifact Signing instead, obtain a verified signing account, signing profile and authorized signer identity. Configure Tauri signCommand and sign the worker through that provider before packaging. Verify the final files on the signing runner.
- The REPLAYX Tauri updater signing key must also be available through its existing secret channel. The updater signature covers the final Authenticode-signed installer bytes. Keep both signing systems' credentials out of the repository. SmartScreen reputation is separate.

See the [Tauri signing guide](https://v2.tauri.app/distribute/sign/windows/) and [Windows Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file).
